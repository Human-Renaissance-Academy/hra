# HRA 1인 운영 체크리스트

> 운영 목표: **Production 웹 1개만 상시 실행**, 자동 점검으로 문제를 알아차리고, 바쁠 때도 최소 단계로 복구한다.
> 구축·검증 여부를 표시하는 문서가 아니다. 실제 서비스 권한/백업/알림 상태는 #284, #280, #333에서 확인한다.

## 처음 한 번 확인할 항목

- [ ] 운영 도메인, Vercel 프로젝트, 연결된 Neon·Blob(공개/비공개) 자원과 **복구 접근권한**을 안전한 장소에 기록한다. 비밀번호·DB URL·토큰을 GitHub에 적지 않는다.
- [ ] 관리자 계정·서비스 계정 MFA 및 비상 복구 절차, 요금 결제/무료 한도·사용량 경고의 수신처를 확인한다.
- [ ] DB 백업이 실제로 활성화되어 있는지, 보존 기간과 복원 시 예상 데이터 손실 범위를 확인한다. **격리된 곳에 복구 테스트한 증거가 없다면 '복구 검증 완료'로 표시하지 않는다.** Blob 파일의 복원/삭제 정책도 별도 확인한다(#280/#142).
- [ ] 운영 Production DB/Blob 자격증명이 Local·CI·Preview에 사용되지 않는지 확인한다(#279).
- [ ] Production 배포 성공과 **정확한 배포 커밋 SHA**가 연결된 공개 smoke·실패 알림(#333)이 실제 수신처에 전달되는지 확인한다.
- [ ] 외부 서비스 장애·무료 한도 초과·비밀값 만료 등에 대한 책임자 및 알림 경로를 정한다. 24시간 실시간 대응을 보장할 수 없다면 그 수준을 서비스 운영 약속으로 하지 않는다.
- [ ] 현재 활성 Cron과 실제 삭제 동작, 데이터 보존/파기 허가 상태를 확인한다. 미사용 Cron을 추가하지 않는다(#494).

## 평소에는

**매일 수동 대시보드 확인을 기본 업무로 만들지 않는다.** 알림이 없으면 자동 검증 결과와 운영 지표를 필요할 때만 확인한다. 다만 자동 알림이 실제로 작동하는지 주기적으로 확인하고, 보안 패치·비용·용량·백업 상태는 소유자가 감당할 수 있는 정기 간격에 검토한다. '완전 무인'이나 자동 복구를 보장하는 구조는 아니다.

- 일반 코드 변경: PR → 최신 CI·필수 리뷰 → main 병합 → Vercel Production 배포 → 배포 SHA/공개 smoke 확인.
- 운영 DB가 바뀌지 않는 변경에는 마이그레이션 승인 작업을 매번 추가하지 않는다.
- 운영 DB가 바뀌는 배포만 [DB 변경 배포 게이트](../developer/database-change-procedure.md#db-change-gate)를 따른다: 플래그 꺼진 채 병합 → 백업 확인 → SQL 적용 → 읽기 전용 보고서의 catalog `missing` 0 → 플래그 켜기. 실패하면 플래그를 끈 채 forward-fix하고 자동 `DROP`하지 않는다. 플래그가 없으면 SQL을 먼저 적용·확인한 뒤 병합한다.
- Preview가 필요한 날에만 비운영 Test DB·합성 자료로 검증하고, 평소에는 CI를 사용한다.
- 실제 사용자가 없는 기능·Android 출시 범위를 넘는 모바일 확장·불필요한 타사 서비스는 추가하지 않는다([Android 출시 재개 결정(#576)](../decisions/2026-11-20-android-play-release-resume.md)이 대체한 범위를 제외하고 #491 [동결 결정](../decisions/2026-11-19-mobile-api-freeze.md) 취지를 유지).

## 알림이 왔을 때

1. 먼저 **실제 운영 실패인지, 의도된 실패/테스트인지** 확인한다. 배포 SHA, 경로, 상태코드, 첫 실패 시각과 마지막 정상 시각을 구분한다. [공개 점검 절차](production-smoke.md)를 따른다.
2. 운영 Vercel 배포 상태와 애플리케이션 오류 로그를 확인하되 개인정보, 토큰, 전체 DB URL을 이슈에 붙이지 않는다.
3. 최근 배포 직후 발생했다면 **이전 정상 웹 버전으로 되돌리는 방법**을 확인한다. 단, DB 스키마·파일·데이터 변경은 앱 버전 되돌리기로 자동 복구되지 않는다.
4. 로그인/권한/Private Blob/개인정보 관련이면 쓰기 범위를 안전하게 제한하고 원인을 확인한다. 데이터를 임의 재생성하거나 백업으로 무조건 덮어쓰지 않는다.
5. DB 관련 오류이면 먼저 대상 DB·마이그레이션 이력·최근 백업/복구 상태를 확인한다. 실패한 SQL을 자동 반복하지 않는다(#280).
6. 원인·영향·조치·복구 여부를 짧게 기록하고, 동일 유형의 반복 장애라면 **알림/가드 또는 근본 해결**을 추가한다. 설명만 길게 쓰는 운영 문서는 만들지 않는다.

## 분명히 남겨 둘 미완료 항목

- Production DB 및 Blob의 **실제** 백업·복구 가능성은 점검 증거가 있어야 완료다(#280/#142).
- Preview 홈의 2026-11-14 HTTP 500은 #522 이후 코드 계약상 Preview 거부 응답(HTTP 503·`no-store`·`noindex`, `src/lib/preview-boundary.ts`)으로 바뀌었다. 다만 실제 Preview 배포의 응답·자격증명 분리 측정([운영 확인 절차 §2](production-verification-runbook.md#preview-separation))이 남아 있으므로 Preview 데이터 격리가 해결됐다고 가정하지 않는다(#279).
- 실제 수신 가능한 알림·비용 한도·권한 복구 연락 경로는 설정값을 확인해야 한다(#333/#284).
- CI 간소화는 필수 보안·배포 후 알림 유지 여부를 검증한 다음 진행한다(#492).
