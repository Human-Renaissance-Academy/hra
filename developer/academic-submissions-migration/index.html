    과제 최종 제출·업로드 의도 변경 절차¶

    최종 제출·파일·업로드 상태의 DB 구조를 설치하거나 변경할 때 읽는다. 업로드 의도는 전송을 준비한 기록이고 최종 제출은 제출이 확정된 기록이다. DB는 최종 제출·파일 한 개·소비된 업로드 의도가 함께 존재하도록 강제한다. 이처럼 여러 변경이 전부 성공하거나 전부 취소되는 성질을 원자성이라고 한다.

    아래는 구현된 #148 저장 단계의 계약이다. 사용자 동작부터 이해하려면 학생 UI를 먼저 읽고, 실제 서버 연결은 업로드와 최종화를 함께 확인한다. DB 적용 전에는 공통 변경 절차와 전체 SQL 적용 순서를 따른다.

    이 문서는 #148의 G1 저장 계약이다. migrate-academic-students.sql(#144), migrate-academic-assignments.sql(#147) 적용 후 scripts/migrate-academic-submissions.sql을 적용한다. 앱 진입점·비공개 Blob 검증·서버 인가(#151/#152)는 별도다. 개인정보 보존기간 #142는 미정이므로 이 변경만으로 운영 제출 기능을 활성화하지 않는다. 최종 기록 자동삭제를 도입하지 않는다.

    모델과 쓰기 계약¶

    테이블 목적과 제약
    assignment_upload_intents 대상·검증된 로그인 계정·서버가 지정한 저장 키와 만료 시각. 저장 키는 전역 유일. 미검증 INTENDED에서 서버 검증 후 VERIFIED, 최종화 시 CONSUMED로 전환한다. 미검증 상태가 만료되면 EXPIRED로만 종료할 수 있다.
    assignment_submissions 최종 완료 행만 저장. 대상당 1건, 전역 UUID submission_key당 1건, 업로드 의도당 1건. 복합 FK로 대상·제출자·업로드 의도 소유자를 일치시킨다.
    assignment_submission_files 제출당 단일 PDF. 원본 파일명과 저장 키를 분리하고 MIME, 실제 바이트 수, SHA-256 소문자 64자리 해시를 저장한다. 1~52,428,800바이트(50MiB)만 허용한다.

    모든 FK는 ON DELETE RESTRICT다. 사용한 업로드 의도와 최종 제출·파일은 변경·삭제하지 못한다. 학적의 학생·기수 변경은 #147이 차단하고, 업로드 이력이 생긴 학생의 연결 계정 변경도 별도 이관 절차 없이는 차단한다. 과거 최종 기록의 제출자를 조용히 교체하지 않는다.

    현재 src/lib/db/schema.ts는 academic-submissions.ts의 세 테이블과 enum을 재수출하므로 Drizzle Kit가 이를 발견한다. 테이블 정의만으로 트리거와 함수를 대체할 수 없다. 빈 개발 DB에서 db:push를 사용했더라도 범위 SQL 적용과 카탈로그 확인이 필요하다.

    트랜잭션 격리수준¶

    업로드 의도 생성·검증·최종화와 학생 계정 연결 변경은 READ COMMITTED에서만 실행한다. 소유권 검사 공통 함수와 계정 변경 트리거가 더 높은 격리수준을 거부한다. 계정 변경 검사는 참조 행 조회보다 먼저 실행되며 현재 참조가 없는 학생에게도 적용한다.

    REPEATABLE READ에서는 빈 업로드 목록으로 snapshot을 확보한 뒤 다른 트랜잭션이 최종 제출해도 오래된 snapshot에 해당 이력이 보이지 않는다. 따라서 단순한 참조 존재 검사만으로 계정 연결 변경을 허용하면 최종 제출의 소유권이 깨질 수 있다. READ COMMITTED와 기본 VOLATILE 함수의 내부 쿼리 snapshot으로 새로 커밋된 참조를 확인하고, 소유권 검사의 학생·학적 행 잠금으로 반대 방향의 계정 변경 경쟁도 직렬화한다. 전역 DB 격리수준을 변경하지 않고 허용되지 않는 호출을 오류로 롤백한다.

    현재 권한 재검증과 철회 경합¶

    앞선 조회 #150이나 업로드 검증이 성공했더라도 의도 생성·검증·최종화 DB 호출마다 현재 users.role = MEMBER, 본인 학생 계정 연결, ENROLLED, ended_at IS NULL, enrolled_at·학적 created_at이 DB 현재 시각 이하임을 다시 확인한다. 같은 키 재시도도 현재 권한 검사를 먼저 실행한다. 역할/학적이 철회되면 새 최종화와 재시도를 거부하되 기존 최종 기록은 보존한다. 과제는 이미 공개된 PUBLISHED/CLOSED이고 공개 시각이 DB 현재 시각 이하여야 한다. 새 최종화·검증·의도 생성에는 별도로 공개 상태와 마감도 적용한다.

    역할은 계정 행 FOR SHARE, 학적과 학생도 FOR SHARE로 잠가 트랜잭션 종료까지 보호한다. FOR KEY SHARE만으로는 역할·종료 시각 같은 비키 컬럼 UPDATE를 막지 못하므로 사용하지 않는다. 철회가 먼저 해당 행을 잠그면 제출 함수는 기다린 뒤 새 상태를 읽고 거부한다. 제출 함수가 먼저 잠그면 철회가 기다리고 제출 커밋 후 적용된다. 권한 판단과 최종 기록 쓰기가 이 순서로 직렬화된다.

    서버 호출용 변경 함수의 잠금 순서는 대상 → 계정 → 학생/학적 → 과제 → 업로드 의도다. 검증 함수는 불변 대상 정보를 먼저 읽고 대상/소유권 잠금 후 의도를 다시 잠가 상태를 재확인한다. 기존 사용자 역할 변경은 users만, 학적 종료는 enrollment만 갱신하므로 이 경합에는 역순의 순환 대기가 없다. 향후 여러 테이블을 동시에 변경하는 관리 트랜잭션도 계정을 먼저 잠근 뒤 학생/학적을 갱신해야 한다. 임의 직접 DML이나 다른 순서의 복합 관리 트랜잭션까지 무조건 무교착임을 보장하지 않으며 PostgreSQL이 검출한 deadlock은 트랜잭션 전체 롤백 후 재시도한다. 이러한 실패가 부분 최종 기록을 커밋시키지는 않는다.

    서버가 사용하는 함수¶

    업로드 의도 생성¶

    서버가 인증 계정과 대상의 소유권·공개 상태·마감을 확인한 뒤 assignment_upload_intents에 대상 ID, 계정 ID, 새 저장 키, 짧은 만료 시각을 INSERT한다. state와 검증 메타는 제공하지 않는다. DB가 생성 시각을 확정하고 대상 학적 학생의 user_id 일치 및 공개·마감을 재확인한다. 저장 키는 상대 객체 키이며 URL·상위 디렉터리·제어 문자를 거부한다. 저장소/접두어 허용목록과 예측 불가능한 키 생성은 서버 책임이다.

    verify_academic_assignment_upload¶

    인수는 (intent_id uuid, actor_id uuid, file_name text, file_mime text, file_size integer, file_checksum text), 반환은 같은 의도 UUID다. 인증된 서버가 비공개 Blob의 정확한 저장 키, 객체 소유권, 실제 크기, PDF 내용과 SHA-256을 검증한 후 호출한다. 사용자 입력 URL·확장자·Content-Type만 신뢰해서는 안 된다.

    DB는 본인 INTENDED 의도를 잠그고 메타와 VERIFIED 상태를 기록한다. 검증 시각은 DB 시각이며 만료 이후 검증은 실패한다. 이 함수는 실제 외부 객체를 읽지 않으며 호출 자체가 Blob 검증의 증거는 아니다. 현재 서버 연결은 #151의 실제 객체 검증과 #152의 최종화 서비스가 담당한다.

    finalize_academic_assignment_submission¶

    인수는 (target_id uuid, actor_id uuid, intent_id uuid, request_key uuid), 반환은 최종 제출 UUID다. 서버 인가 후 호출하며 임의 계정 ID를 클라이언트에서 전달받아 신뢰하지 않는다.

    1. 대상 행을 잠그고 현재 MEMBER 역할·활성 학적·연결된 본인 계정을 재확인한다.
    2. 현재 권한이 유지되고 같은 UUID 키·대상·계정·의도이면 원본 제출 ID를 반환한다. 응답 유실 복구는 과제 종료·마감 이후에도 성공한다. 키 재사용 시 다른 의도·대상·계정이면 실패한다.
    3. 새 키이지만 이미 제출한 대상이면 실패한다. 따라서 동시 같은 키는 같은 결과로 성공하고 다른 키는 하나만 성공한다.
    4. 공개·마감·의도 소유권·만료·VERIFIED를 확인하고 DB 시각을 최종 제출 시각으로 기록한다. 마감 정각부터 실패한다.
    5. 최종 행과 검증 메타의 파일 1건을 INSERT하고 의도를 CONSUMED로 전환한다. 파일 INSERT 실패 시 함수 호출 전체가 롤백된다.

    지연 제약 트리거는 COMMIT 또는 SET CONSTRAINTS ALL IMMEDIATE에서 최종 행·파일·소비 의도의 존재와 메타 일치를 검사한다. 직접 INSERT해도 파일 없는 최종 행이나 단독 소비 상태를 커밋할 수 없다. 완료 UI는 함수 결과를 포함한 트랜잭션 커밋 성공 뒤 표시한다. 외부 객체 업로드는 DB 트랜잭션과 묶이지 않으므로 미사용 객체 정리는 별도 수명주기에서 수행하되 최종 참조를 먼저 확인한다.

    세 서버 호출용 함수는 SECURITY INVOKER이고 PUBLIC 실행 권한을 회수한다. 운영 앱 DB 역할에 필요한 테이블 권한과 함수 실행 권한을 별도 승인한 뒤 부여한다. DB 관리자/테이블 소유자는 트리거를 변경할 수 있으므로 신뢰 경계 내부다. 일반 사용자 브라우저에 DB 접속정보를 제공하지 않는다.

    적용·검증·복구¶

    1. DB 변경 절차에 따라 백업 및 별도 DB 복원을 확인한다. 운영 적용 전에 #142 및 서버 인가·Blob 검증 준비를 확인한다.
    2. 격리 DB에서 #144 → #147 → #148 순서로 실행한다. 기존 운영 DB에 broad db:push를 실행하지 않는다.
    3. psql -X -v ON_ERROR_STOP=1 -f scripts/migrate-academic-submissions.sql로 실행한다. 전체 트랜잭션과 advisory lock, 제한시간을 적용한다.
    4. 동일 스크립트 재실행은 컬럼·타입·NULL·기본값·CHECK·FK·UNIQUE·인덱스/RLS 구조가 같을 때 성공한다. 트랜잭션 범위의 hra_submission_expected 비교 스키마로 차이를 검사하며 다른 구조를 자동 보정하지 않는다. 불일치하면 신규 생성까지 롤백한다. 동명 비교 스키마가 이미 있으면 실패하며 이 스크립트가 새로 만든 비교 스키마만 삭제한다. 함수·지정 트리거는 현재 버전으로 교체된다.
    5. HRA_TEST_PG_BIN=/opt/homebrew/opt/postgresql@18/bin npx vitest run tests/unit/academic-submission-postgres.test.ts로 격리 PostgreSQL 검증을 실행한다. 운영 접속정보는 읽지 않는다.
    6. 이미 최종 자료가 있다면 테이블 DROP이나 이전 모델로의 역마이그레이션을 하지 않는다. 트랜잭션 실패는 자동 롤백하며, 커밋 이후 수정은 백업 복원 연습 후 별도 forward-fix로 수행한다. 복구는 파일 원본과 DB 참조를 함께 확인한다.

    기존 제출·파일·소비 의도 또는 학생 계정 바인딩에 부정합이 있으면 재실행을 거부한다. 자료가 있는 상태에서 오류를 숨기기 위한 제약 삭제나 임의 UPDATE를 하지 않는다.

    재제출 이력 확장¶

    제출 UUID와 파일 UUID는 업무 키인 대상 ID 및 멱등 키와 분리했다. 향후 G3에서 허용된 재제출을 추가할 때 기존 제출·파일 ID를 유지한 채 대상의 단일 제출 UNIQUE를 버전/현재 제출 참조 모델로 확장할 수 있다. 기존 ID를 삭제하거나 덮어쓰는 방식은 감사·다운로드 참조와 멱등 응답을 깨뜨리므로 사용하지 않는다. 현재 G1에서는 재제출을 허용하지 않는다.
