    학사 감사·요청 추적·운영 상태¶

    학사 기능의 장애를 조사하거나 운영 상태를 점검하는 개발자가 읽는다. 감사 기록은 누가 어떤 업무 변경을 확정했는지 남기는 DB 기록이고, 관측 로그는 요청이 어느 단계에서 성공·거부·실패했는지 찾는 실행 기록이다. 화면에 표시된 요청 참조로 관련 로그를 찾되, 로그 한 줄을 제출 확정이나 파일 수신 완료의 증거로 사용하지 않는다.

    현재 코드에는 구조화 로그와 승인자 전용 상태 API가 연결되어 있다. 아래에서 명시한 일부 지표는 아직 누적 원장이 없어 null이며, 운영 로그 보존·알림·백업 정책의 완료를 뜻하지 않는다. 오류 조사에는 요청 참조 → 상태 API → 관련 기능 문서 순서로 접근한다. 정책은 학사 개인정보 보존 문서, 실제 검증은 G1 품질 게이트를 함께 확인한다.

    적용 경계¶

    DB의 성공 감사는 기존 원자적 SQL 함수가 계속 담당한다. 서버 관측 이벤트는 요청 실패·거부·재시도와 요청 참조를 연결하며, DB 감사의 대체 원장이 아니다. 로그 전송이 실패해도 이미 커밋한 학생 등록·계정 연결·과제 변경을 실패로 되돌리지 않는다.

    현재 연결된 작업은 학생 등록(#146), 승인 계획 적용(#145), 과제 생성·수정·공개·종료·조회(#149), 업로드 의도·토큰·검증·취소·공급자 수신·정리(#151), 제출 최종화(#152), 개인 파일 인가·전송(#153), 운영 상태 조회다. 파일 인가와 실제 스트림 완료·중단은 서로 다른 사실이며 AUTHORIZED를 수신 완료로 계산하면 안 된다.

    명부의 목록·상세·기수 조회도 인증된 지정 계정의 현재 DB 역할을 조회 SQL에서 확인한다. 권한을 잃은 요청의 집계를 빈 명부 성공으로 표시하지 않는다.

    이벤트와 요청 참조¶

    src/lib/academic-observability.ts는 다음 필드만 새 객체로 구성한다. 입력 객체를 펼치거나 오류를 직렬화하지 않는다.

    필드 값
    schemaVersion 고정 1
    action, resourceType, outcome 코드의 고정 enum
    actorUserId 실제 세션·대상 인가 성공 후 연결한 UUID, 그 전에는 null
    resourceId, requestId 검증된 UUID 또는 null
    timestamp 서버 생성 UTC 시각
    correlationId 매 요청 서버가 새로 생성한 UUID
    failureCode, sqlState 허용 목록의 고정 코드 또는 null
    retryCount 호출자가 알고 있는 0~1,000,000의 정수 또는 null

    referenceId 응답과 correlationId 로그가 같은 요청을 가리킨다. HTTP 응답은 같은 값을 X-Request-Id에도 넣는다. 공급자 SDK의 토큰·수신 응답과 파일 본문 응답은 기존 본문 계약을 유지하며 헤더로 참조를 전달한다. 사용자 입력의 correlationId는 서버 관측 참조로 사용하지 않는다. 과제 변경 SQL에는 서버 관측 참조를 전달하고, DB의 멱등 재실행은 기존 성공 감사와 requestId로 연결한다. 같은 요청을 재시도할 때 관측 참조는 새로 생성되지만 원래 성공 감사는 중복 생성하지 않는다.

    최종 제출이 호출하는 파일 검증 관측기는 서버 참조만 공유한다. fork()로 만든 관측기는 actor와 실패 상태를 상속하지 않고 파일 검증 경로에서 다시 인가한다. 따라서 사용자에게 반환한 최종 제출 참조로 검증 실패 이벤트까지 찾을 수 있지만, 검증 완료를 제출 완료로 혼동하지 않는다.

    학생 제출·업로드/취소 실패와 관리자 명부·초안·공개·종료 오류 화면은 서버 응답의 referenceId를 기존 오류 메시지와 별도로 요청 참조: …로 표시한다. 기존 alert/live 영역을 유지하며, 폼·저장소의 요청 키나 예외 객체에서 참조를 추정하지 않는다. 서버 응답이 없는 통신 오류와 브라우저 자체 입력 오류에는 참조를 새로 만들지 않는다. #145 계정 연결은 현재 별도 UI가 없고 서버 액션 응답에 참조를 제공한다.

    승인 거부는 DENIED, 인가 성공은 AUTHORIZED, SQL 성공은 COMPLETED, 알려진 재실행은 REPLAYED다. 명부 등록 SQL은 재실행 여부를 반환하지 않아 등록 액션의 COMPLETED는 성공한 호출을 뜻한다. 유일 등록 건수는 academic_roster_registrations에서 확인한다. 인가 설정의 승인자 UUID를 비로그인 실패의 actorUserId로 기록하지 않는다.

    공급자 callback과 cron 정리에는 사용자 세션이 없으므로 actor는 null이다. callback의 AUTHORIZED는 SDK 서명 검증을 마쳤다는 뜻이며 사용자 로그인이나 PDF 검증을 뜻하지 않는다. 수신 callback은 기존 원장에 멱등 기록하고, 중복 callback마다 COMPLETED를 남긴다. 파일 읽기의 requestId는 DB의 원자적 읽기 감사 UUID다. 정상 크기의 스트림 EOF는 COMPLETED, 공급자 읽기 오류·크기 불일치는 STREAM_INTERRUPTED, 클라이언트 취소는 CANCELLED로 기록한다. 정상 EOF도 브라우저가 파일을 저장하거나 사용자가 읽었다는 증거는 아니다.

    원본 error, cause, message, SQL, params, 이름, 이메일, 파일명·경로·URL, 본문, 쿠키와 토큰은 서버 로거에 전달하지 않는다. 실패 이벤트도 새 고정 오류와 위 필드만 logServerError에 전달한다. 실제 Drizzle 오류와 악성 getter/toJSON을 넣은 회귀 테스트로 이 경계를 확인한다.

    승인자 전용 읽기 상태 API¶

    GET /api/academics/health는 실제 로그인과 서버에 지정된 학사 승인자 일치를 확인한다. ACADEMIC_ENABLED=true가 필요하다. 홈페이지 ADMIN 역할만으로는 접근할 수 없다. SQL 집계 시 현재 DB 역할도 ADMIN·FACULTY·MEMBER 중 하나인지 재검사한다. PENDING 등으로 철회되면 세션 정보가 남아 있어도 403이다.

    응답은 Cache-Control: no-store이며 개인별 행·파일 키·이름을 반환하지 않는다. #148/#151 표가 없거나 쿼리에 실패하면 503과 고정 준비 안내만 반환한다. 준비되지 않은 지표를 0으로 바꾸지 않는다.

    지표 의미
    unfinishedCount INTENDED 또는 VERIFIED인 업로드 의도 수. 이미 시간이 지난 의도도 포함
    expiredCount CONSUMED 이외이면서 DB 시각 기준 만료된 의도 수
    verifiedUnsubmittedCount 검증 후 최종 제출되지 않은 VERIFIED 수
    cleanupClaimedCount 정리 선점 후 deleted_at이 없는 원장 수. 진행 중·실패를 구별하지 못함
    cleanupPendingCount 만료+5분 경과, 미제출·미참조, 미선점·미삭제 수
    deletedCount 삭제 확인 시각이 기록된 수. 공급자 전체 객체 부재를 보증하지 않음
    cleanupFailureCount, cleanupRetryCount null: 기존 원장에 영속 실패/시도 횟수가 없어 미수집

    현재 상태는 PARTIAL, 정리 시도 지표는 LOG_ONLY다. null을 0으로 해석하거나 정리 실패가 없다고 보고하면 안 된다. 로그 집계는 이벤트 수이며 영속 시도 원장을 대체하지 않는다. 배포 플랫폼 로그 보존·검색 한계도 별도로 확인한다. 정확한 누적 실패/재시도 집계에는 별도 승인된 원장 확장이 필요하다.

    점검·알림·재시도¶

    1. 승인자 세션으로 API 응답 상태와 요청 참조를 확인한다. 503이면 승인된 migration 설치 상태와 DB 연결부터 확인한다. 403을 우회하는 별도 관리 계정을 만들지 않는다.
    2. 만료 또는 검증 후 미제출 건수가 연속 증가하면 사용자 재시도 실패·마감·쓰기 gate·Blob 장애를 고정 실패 코드와 요청 참조로 확인한다. 운영 알림의 수신자·임계값은 승인 후 설정하며 이 변경은 외부 전송을 활성화하지 않는다.
    3. 정리 선점 수가 줄지 않으면 진행 중인지 로그의 정리 완료·실패 이벤트와 대조한다. 선점만으로 실패 횟수를 추정하지 않는다. 기존 선점·삭제 확인 이력이 있는 의도를 다시 처리하면 RETRY를 남기지만 누적 시도 횟수는 모르므로 retryCount는 null이다. dry-run·미선점·비활성은 SKIPPED이며 삭제 성공으로 계산하지 않는다. 정리 실패/재시도 로그를 집계할 때 correlationId와 대상 UUID로 같은 실행의 중복 수집을 제거한다.

    4. 151 정리는 기본 비활성·기본 dry-run을 유지한다. 상태 조회가 정리·재시도·삭제를 실행하지 않는다. 실제 삭제는 별도 운영 승인과 두 쓰기 플래그가 필요하며, 만료+유예·미참조·DB 선점·ETag 대조 조건을 모두 유지한다. 최종 제출 보호를 해제하는 수동 SQL을 실행하지 않는다.¶

    복구 확인 절차¶

    DB 백업이 Blob 본문을 복원해 주지는 않는다. DB 최종 제출 행의 키·크기·해시와 공급자의 객체가 일치하는지 별도로 검증해야 한다. 기존 RESTRICT·불변 트리거·지연 제약과 DB 권한을 복원 후에도 보존한다.

    격리 DB·합성 파일로 검증 가능한 항목¶

    다음 명령은 운영 URL이나 환경 파일을 읽지 않고 소켓 전용 임시 PostgreSQL에서 실행한다. 테스트는 별도 빈 restore_target DB에 dump를 복원하고 합성 제출의 DB 지문·최종 1회 제약·파일 크기/해시 참조를 비교한다. 덤프와 참조 값은 출력하지 않으며 임시 클러스터는 종료 후 삭제한다.

    HRA_TEST_PG_BIN=/opt/homebrew/opt/postgresql@18/bin npm test -- tests/unit/academic-operations-postgres.test.ts
    • [ ] 운영 복구 전에 승인된 백업의 복원 대상이 빈 격리 DB인지 확인한다. 운영 DB에 덮어쓰지 않는다.
    • [ ] 승인된 DB 역할·필수 확장·SQL 함수·트리거·제약·PUBLIC 권한 회수를 포함해 복원한다. 테스트의 --no-owner --no-privileges는 합성 로컬 복원에만 사용하며 운영 권한 복원 증거가 아니다.
    • [ ] 학생/등록/대상/최종 제출/파일 행의 건수와 비공개 지문을 복원 전후 비교한다. 이름·이메일·키·URL·덤프를 로그나 이슈에 붙이지 않는다.
    • [ ] 최종 제출마다 의도 CONSUMED, 제출/파일 1개, 같은 저장 키·크기·해시인지 내부에서 대조하고 결과 건수만 보고한다.
    • [ ] 별도 승인된 private Blob 검증으로 접근 상태·실제 스트림 크기·PDF 형식·SHA-256을 비교한다. URL·토큰·본문을 출력하지 않는다. 누락/불일치 건수만 보고하고 복구 가능한 원본의 존재를 확인한다.
    • [ ] 새 요청·같은 키 재실행·다른 키 중복 제출·권한 철회를 합성 계정으로 확인한다. 실제 개인정보 요청을 복구 시험에 사용하지 않는다.

    #142 정책 확정이 필요한 미완료 항목¶

    • [ ] 학생 정보·제출 파일·승인 감사·관측 로그 각각의 보존 기간과 시작 시점
    • [ ] 삭제 요청·분쟁 보류·탈퇴·수료 시 처리 순서와 승인자
    • [ ] DB 백업 보존 기간·삭제 반영 주기·복구 시 재삭제 정책
    • [ ] Blob 백업/복원 가능 범위와 복구 목표·비용·보존 기간
    • [ ] 운영 복구 시험 일정·실행 권한·비공개 증거 보관 위치

    사용자가 지정한 승인자는 설정하지만 위 기간을 임의로 확정하지 않는다. 이 기능은 자동 파기, 백업 보존 설정 변경, cron 활성화 또는 운영 데이터 저장 gate 해제를 수행하지 않는다.
