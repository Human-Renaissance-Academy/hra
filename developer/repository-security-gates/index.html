    저장소 secret·의존성 게이트¶

    이 검사는 공개 저장소의 지속 검증이며 실제 secret의 부재나 모든 취약점의 비도달성을 증명하지 않는다. GitHub native secret scanning·push protection의 실제 상태는 아래 API 관측을 확인한다. standalone 검사는 별개의 검사이며 해당 기능의 활성화를 증명하지 않는다.

    Secret 검사¶

    node scripts/scan-repository-secrets.mjs --gitleaks /absolute/path/to/gitleaks

    Linux x64 Gitleaks 8.30.1을 사용한다. 공식 release archive SHA256은 551f6fc83ea457d62a0d98237cbad105af8d557003051f41f3e7ca7b3f2470eb, 압축 해제한 실행 파일 SHA256은 88f91962aa2f93ac6ab281d553b9e125f5197bbbce38f9f2437f7299c32e5509다. 실행기는 binary hash와 version을 다시 확인한다. 공식 release의 checksum을 검증한 파일만 전달한다. Gitleaks upstream은 기능 개발을 종료하고 보안 유지보수를 제공하므로 버전 고정만으로 미래 패턴 탐지를 보장하지 않는다.

    기본 엔진 규칙을 유지하고 현재 Git 추적 파일의 작업 트리 내용과 --all --full-history의 로컬에 fetch한 reachable refs를 각각 검사한다. shallow checkout, 누락된 이력 객체, scanner 실패, 보고서 누락/잘못된 JSON은 실패다. CI는 전체 이력을 fetch해야 한다. 삭제된 remote refs·다른 fork·미추적 파일·운영 secret 저장소까지 검사했다고 주장하지 않는다. 전체 reachable refs라 해도 과거 유출 대응을 대체하지 않는다.

    합성 예외는 generic-api-key 규칙에 대해 tests/unit/academic-upload-server.test.ts와 tests/unit/api-v1-academic-uploads-route.test.ts의 각 파일에 고정된 정확한 값의 SHA256을 함께 확인하는 두 조합이다. 기존 서버 테스트는 과거 세 도입에서 같은 vi.stubEnv의 명시적 fixture 표식과 @vercel/blob mock을 확인했다. v1 테스트의 추가 값도 mock 저장소와 로컬 SDK HMAC 서명에만 사용하는 합성 값임을 확인했다. 다른 값·파일·규칙이나 두 파일의 값을 서로 바꾸는 경우는 계속 탐지하며 원문을 정책에 재기록하지 않는다. tests/**나 규칙 전체를 제외하지 않는다.

    매 실행의 실제 엔진 canary는 임시 Git 저장소의 tests/unit/academic-upload-server.test.ts 경로에 다른 새 secret을 넣어 source에서 탐지하고, 삭제 commit 이후에도 history에서 탐지되는지 확인한다. v1 경로의 정확한 값·파일·규칙 예외는 단위 회귀와 실제 source/history 검사로 검증한다.

    stdout에는 scope별 탐지 수·합성 예외 수·canary 결과만 쓴다. scanner stdout/stderr와 원문 JSON은 private 임시 디렉터리에서만 처리하고 정상/오류/일반 종료 신호 때 제거한다. SIGKILL/호스트 장애는 cleanup을 보장할 수 없다. CI artifact로 raw report를 업로드하지 않는다. 실제 자격정보가 의심되면 원문을 공개 이슈·댓글·로그에 붙이지 않고 비공개 보안 절차로 전달한다. 이 검사는 history rewrite나 credential 회전을 수행하지 않는다.

    의존성 검토¶

    node scripts/verify-dependencies.mjs
node --test scripts/tests/secret-scan.test.mjs scripts/tests/dependency-policy.test.mjs

    실행기는 credential 환경을 전달하지 않고, 소유 임시 디렉터리의 package/lock 복사본과 비어 있는 npm 설정으로 npm audit --json --package-lock-only --ignore-scripts를 실행한다. registry는 https://registry.npmjs.org로 고정한다. exit 1의 발견과 통신/구문 오류를 구분하며 raw npm 오류는 출력하지 않는다. 설치 파일을 수정하거나 자동 업데이트하지 않는다.

    현행 exact metadata와 권고별 평가·context·기한의 정본은 루트 security/dependency-triage.json과 모바일 security/mobile-dependency-triage.json이다. 현재 결과는 위 CLI(npm run verify:dependencies)의 대상별 출력과 원장을 함께 확인한다. 아래 숫자는 관측일의 기록이며 원장 갱신 때마다 수작업으로 유지하는 별도 정본이 아니다.

    2026-11-14 실제 registry audit는 루트 17 affected package·3 object-advisory entry·24 평가·4 공유 context, 모바일 29·3·54·3으로 두 원장과 정확히 일치했다. 현행 가장 이른 기한은 모바일 2026-11-25(47평가), 루트 2026-11-26(3평가)이다. object-advisory와 전이 링크를 포함한 평가 수는 서로 다르다. 동일 GHSA의 여러 영향 범위/source ID도 별도로 보존한다. package nodes+lock 버전과 advisory ID/source/range 집합은 독립적이다. 모든 nodes×advisory 조합을 실제 영향 경로라고 해석하지 않는다. npm의 dev 값도 실제 운영 도달성을 대신하지 않는다.

    package-lock.json의 모든 resolved는 https://registry.npmjs.org/로 시작해야 한다(워크스페이스 link 제외). 개인 ~/.npmrc나 사내 미러가 만든 외부 피드 주소가 섞이면 DEPENDENCY_LOCK_REGISTRY_INVALID와 설치 경로만 출력하고 차단한다(#432). 외부 주소 자체는 로그에 남기지 않는다.

    루트 원장 변경 이력¶

    UTC 2026-11-05에는 실제 audit가 DEPENDENCY_TRIAGE_CHANGED로 바뀐 원인을 확인했다. GitHub가 minimatch globParts 증폭 권고를 2026-11-04T16:50Z에 정정해 영향 범위가 <11.0.1에서 >=7.0.0 <11.0.1로 좁혀졌고, npm audit source도 1244012에서 1244623으로 바뀌었다. 첫 수정 버전은 여전히 11.0.1이며 10.x 최신 10.2.6도 영향 범위다. 이에 루트 minimatch 3.1.5와 이를 통해서만 영향받던 eslint·@eslint/config-array·@eslint/eslintrc·@eslint-community/eslint-utils·@next/eslint-plugin-next·eslint-plugin-import·eslint-plugin-jsx-a11y·eslint-plugin-react 8개 패키지와 이 경로의 전이 링크가 audit에서 빠졌다. 원장에서 해당 평가 22건과 minimatch:1244012를 제거하고 minimatch:1244623 1건을 추가했다(26패키지·3 object-advisory·48평가·4context → 18·3·26·4). lockfile과 package.json은 바꾸지 않았다. 남은 @typescript-eslint/typescript-estree·hanspell 내부 10.2.5 경로의 tooling-minimatch-glob 평가 15건은 실제 registry로 다시 확인해 검토일을 2026-11-05로 갱신하고, 개발 도구 전용 4주를 넘지 않는 기존 기한 2026-12-03을 유지했다. shadcn-ts-morph-glob 3건은 경로·무패치 상태가 그대로이고 판단문을 바꾸지 않아 검토일과 기한(2026-11-26)을 그대로 뒀다. 다른 context도 바꾸지 않았다.

    한국 시간 2026-11-04 저녁에는 가장 이른 기한(2026-11-19)이 도래하기 전에 해당 평가 6건을 빈 캐시의 실제 registry audit와 npm view로 다시 확인했다.

    • postcss-selector-parser 권고는 6.x 수정본 6.1.5가 있지만 최신 @tailwindcss/typography 0.5.20이 6.0.10을 정확히 고정해 npm update로 적용되지 않는다. upstream의 6.1.5 상향 PR도 아직 병합되지 않았다. 이에 package.json에 typography 하위로만 범위를 제한한 overrides(postcss-selector-parser: ^6.1.5)를 추가하고 lockfile의 해당 항목 하나만 6.1.5로 바꿨다. 6.0.10과 6.1.5의 런타임 의존성(cssesc·util-deprecate)은 같다. 저장소 globals.css와 typography 전체 변형(크기·색상 테마·어두운 배경 반전·제외 클래스·요소 modifier)을 강제로 포함한 입력을 @tailwindcss/postcss로 컴파일한 결과는 갱신 전후 바이트 단위로 같았다. 이에 패키지 2개(postcss-selector-parser·@tailwindcss/typography), 평가 2건, 참조가 없어진 build-css-source-map context를 제거했다(28패키지·4 object-advisory·50평가·5context → 26·3·48·4). shadcn 내부의 postcss-selector-parser 7.1.6은 영향 범위 밖이다.
    • deepmerge 권고는 최신이 여전히 4.3.1이고 권고의 첫 수정 버전도 없다. upstream 수정 PR은 열려 있지만 릴리스되지 않았다. 최신 shadcn 4.23.0·@shadcn/registry 0.2.1도 deepmerge ^4.3.1을 사용한다. 대신 사용면을 다시 확인했다. src/·packages/·next.config.ts·postcss.config.mjs·scripts/·워크플로에는 shadcn·@shadcn/registry·deepmerge·ts-morph의 JavaScript import가 없다. 유일한 참조는 src/app/globals.css의 빌드 시점 CSS @import "shadcn/tailwind.css"와 components.json(CLI 설정)이다. Next 빌드 추적(.next의 *.nft.json 156개)에도 포함되지 않는다. 빌드는 이미 devDependencies인 tailwindcss·@tailwindcss/postcss를 필요로 하고, CI는 모두 npm ci(dev 포함)로 설치한다. --omit=dev·NODE_ENV=production 설치, Dockerfile·런타임 이미지도 없으며 Vercel 기본 설치도 devDependencies를 포함한다. 이에 shadcn을 devDependencies로 옮겼다(lock은 280개 항목의 dev: true 표시만 바뀜). deepmerge·@shadcn/registry·ts-morph 경로가 dev=true가 되어 shadcn-registry-cli 평가 4건은 #424 기준의 개발 도구 전용 4주 주기를 따른다. 검토일 2026-11-04부터 4주를 넘지 않는 2026-12-02로 기한을 정했다. shadcn을 다시 dependencies로 옮기면 audit 스냅샷과 정책 테스트가 함께 실패해 재분류된다.
    • shadcn-ts-morph-glob도 같은 이동으로 dev=true가 되어 사실 서술만 고쳤다. 기한(2026-11-26)은 이번에 늘리지 않았다. 다른 context의 평가와 기한도 바꾸지 않았다.

    한국 시간 2026-11-04에는 모든 평가의 2026-11-05 기한 도래 전에 69평가를 권고별로 재검토했다. 기존 lock 범위 안 수정본을 npm update brace-expansion source-map-js esbuild vite로 적용해 brace-expansion 1.1.21·5.0.12, source-map-js 1.2.2, 루트 esbuild 0.28.2, vite 8.3.5(vitest 전용 개발 의존성, rolldown 1.2.16 동반)로 갱신했고 package.json은 바꾸지 않았다. 실제 audit에서 사라진 brace-expansion 12건, Vite 5건, source-map-js 1건, esbuild Windows serve 권고 1건 등 평가 19건과 참조가 없어진 tooling-brace-expansion·vitest-vite context를 제거했다(31패키지·23 object-advisory·69평가·7context → 28·4·50·5). 남은 4개 권고는 범위 안 수정본이 없거나 정확한 pin으로 적용되지 않아 사용면을 다시 평가하고, 일괄 연장 없이 위험별 기한을 뒀다. reviewedOn은 게이트가 비교하는 UTC 날짜(2026-11-03)로 기록한다.

    재검토 기한의 일반 기준은 실제 registry로 다시 확인한 검토일(reviewedOn)부터 dev=false이거나 수정본이 있는데 적용하지 못한 사용면은 2주, dev=false CLI 전이 경로의 DoS는 3주, 개발 도구 전용(dev=true) 경로는 4주이며 이 기간을 넘겨 정하지 않는다. reviewedOn은 게이트가 오늘 날짜와 비교하는 UTC 날짜로 기록한다.

    현재 P2는 독립 코드 검토를 거치는 사용면 평가이며 모든 high 항목을 면제하는 정책이 아니다. 루트의 재검토 기한은 사용면 위험에 따라 2026-11-26(CLI DoS, 2026-11-03 판단 당시 dev=false)·2026-12-02·2026-12-03(개발 도구 전용 4주)으로 나뉜다. 기한 전에 패치 또는 새 근거를 검토하고 실제 재검토일과 기한을 갱신한다. 단순히 기한을 늘리지 않는다. 확인된 P1은 이 게이트에서 항상 차단하며 수정이 필요하다. 권한 있는 owner의 개별 예외가 필요하다면 별도 검토로 정책을 확장해야 하며 에이전트가 승인 사실을 만들어 통과시키지 않는다.

    공식 근거: npm audit 동작, 각 원장 항목의 GHSA ID. 원장의 source 번호와 범위는 registry 관측 시점 자료이므로 upstream advisory 변경은 재검토를 유발한다.

    모바일 앱 lockfile (#446)¶

    apps/mobile은 루트와 별도로 설치하는 독립 프로젝트이므로 apps/mobile/package-lock.json을 별도 원장 security/mobile-dependency-triage.json으로 검사한다. npm run verify:dependencies는 루트와 모바일 대상을 차례로 같은 방식(소유 임시 디렉터리·빈 npm 설정·공식 registry 고정 audit)으로 검사하고, 대상별 결과를 {"target":"root"|"mobile",...} 한 줄로 출력한다. 한 대상이 실패해도 다른 대상을 계속 검사한 뒤 종료 코드 1로 차단하며, 실패 진단 앞에는 고정된 대상 이름 DEPENDENCY_TARGET <이름>만 붙인다. 공식 registry 검사(#432)·정확 일치·만료·P1 차단 규칙은 루트와 같다. 두 lock의 같은 패키지 이름이 서로 다른 버전·경로를 가지므로 원장을 합치지 않는다.

    모바일 원장의 packages는 사람이 쓰지 않고 실제 audit와 lock으로 dependencySnapshot()을 실행한 결과를 그대로 기록한다. 전이 패키지의 range는 registry의 최신 배포 목록에 따라 달라지므로 개인 npm 캐시가 아니라 빈 캐시(게이트와 같은 조건)로 얻은 audit를 사용한다. 한 패키지가 같은 이름의 전이 패키지를 여러 버전으로 두면(예: 최초 등록 시 test-exclude의 glob 7·10) npm이 같은 링크를 중복 보고한다. 링크 목록은 snapshot 정확 일치로 그대로 고정하고, 평가 키(test-exclude:glob)는 한 번만 요구한다.

    같은 날 #492의 읽기 전용 API 조회에서는 secret_scanning, secret_scanning_push_protection, secret_scanning_non_provider_patterns, secret_scanning_validity_checks, dependabot_security_updates가 모두 disabled였다. Dependabot alerts는 API 204로 활성 상태를 확인했고 automated security fixes는 enabled=false, paused=false였다. 주간 version-update 설정은 security-update 자동 PR 활성이나 실행 성공을 뜻하지 않는다. CodeQL/code scanning 상태는 미확인이다. 이는 관측 기록이며 기능 활성화, 검사 삭제, 권한 완화의 승인이나 제안이 아니다.
