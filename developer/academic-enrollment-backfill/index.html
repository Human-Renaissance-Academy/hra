    회원과 학적의 검증 연결¶

    이미 등록된 학생 명부와 실제 로그인 계정을 연결하는 개발자·운영자가 읽는 절차입니다. 학적은 학생이 어느 기수에 등록되어 있는지 나타내는 관계입니다. 백필(backfill)은 기존 자료에 빠진 연결을 확인된 근거로 채우는 작업이며, 이름이 같다는 이유로 두 사람을 합치는 작업이 아닙니다.

    계정 연결 서비스와 명령줄 도구는 구현되어 있습니다. 명부 자체를 먼저 만들려면 학생 등록을 읽고, 이 문서에서는 승인 계획 작성 → 쓰지 않는 사전 검사(dry-run) → 승인된 대상에 적용 순서로 진행합니다. 실제 운영 실행은 아래 정책·백업·대상 확인 조건을 따릅니다.

    145는 기존 학생 ID와 확인된 회원 ID를 수동 승인한 뒤 연결하고, 계획에 명시된 기수 등록만 추가합니다.¶

    users.role, users.cohortId, 이메일과 OAuth 바인딩은 수정하지 않습니다. 기존 학적도 유지합니다. 이름·이메일·현재 회원 기수 일치로 학생을 생성하거나 계정을 추정하지 않습니다.

    적용 전제¶

    1. 144의 scripts/migrate-academic-students.sql을 격리 개발 DB에서 검증합니다.¶

    2. 같은 DB에 scripts/migrate-academic-enrollment-links.sql을 적용하고 반복 적용을 검증합니다.
    3. 책임자가 본인의 실제 앱 계정 ID를 확인해 ACADEMIC_APPROVER_USER_ID에 지정합니다. 이름이나 최초 ADMIN 행으로 추론하지 않습니다.
    4. 보존·파기 정책(#142), 운영 백업·복구 경로, 승인 계획을 검토한 후에만 운영 저장을 활성화합니다. 현재 예시의 ACADEMIC_ENROLLMENT_WRITES_ENABLED=false를 유지합니다. 코드·격리 DB 테스트 완료는 운영 실행 승인이 아닙니다.

    웹 서비스는 실제 로그인 세션의 승인된 MEMBER·FACULTY·ADMIN 계정과 지정 책임자 ID가 일치해야 합니다. SQL 함수는 실행 중에도 책임자 계정의 존재·승인 역할을 다시 확인합니다. 지정되지 않은 ADMIN은 학사 승인자가 아닙니다. CLI는 DB 접속 권한을 가진 신뢰된 운영자의 오프라인 도구입니다. 계획 파일에 쓴 승인자 ID는 로그인 인증을 대신하지 않습니다. 운영자는 책임자의 별도 신원 확인·승인을 받은 계획만 실행해야 합니다.

    기본 읽기 전용 점검¶

    환경변수는 제한된 로컬 파일이나 PostgreSQL 접속 관리 방식으로 전달합니다. URL·토큰을 명령 인자로 전달하지 않습니다.

    npm run academic:backfill
npm run academic:backfill -- --dry-run --plan=/안전한/경로/승인계획.json

    도구는 대상 DB의 호스트·포트·DB 이름·접속 사용자로 계산한 확인값과 UUID·역할·건수만 출력합니다. 후보, 회원 기수 누락, 미연결 학생, 역할 차이, 학적과 회원 기수 차이, 중복을 보고합니다. 다중 기수 이력으로 생기는 차이는 정상일 수 있으므로 자동 수정하지 않습니다. 계획을 전달하면 각 ID의 존재, 점검 당시 역할·기수 일치, 연결 충돌, 등록 존재를 추가로 대조합니다.

    승인 계획¶

    학생은 승인 명부로 미리 등록되어 있어야 합니다. 표시 이름이나 증빙 사본을 이 계획에 넣지 않습니다. 아래 UUID는 형식 설명용이며 실제 운영 계정이 아닙니다.

    {
  "requestId": "10000000-0000-4000-8000-000000000001",
  "approverUserId": "20000000-0000-4000-8000-000000000001",
  "approvalReferenceId": "30000000-0000-4000-8000-000000000001",
  "verificationMethod": "IN_PERSON",
  "links": [{
    "studentId": "40000000-0000-4000-8000-000000000001",
    "userId": "50000000-0000-4000-8000-000000000001",
    "cohortId": "60000000-0000-4000-8000-000000000001",
    "expectedRole": "MEMBER",
    "expectedCohortId": null
  }]
}

    확인 방식은 대면 확인 IN_PERSON 또는 사전에 검증된 연락 경로 VERIFIED_CONTACT입니다. 승인 근거 참조는 외부 승인 절차의 UUID이며 연락처·증빙 원문·임의 메모를 저장하지 않습니다. expectedCohortId는 현재 회원 값의 변경 감지용입니다. 실제 등록은 명시한 cohortId만 사용합니다. PENDING 계정은 연결하지 않으며, MEMBER뿐 아니라 확인된 과거 학생의 FACULTY·ADMIN 계정도 명시 승인할 수 있습니다. 역할 변경은 별도 홈페이지 관리 절차이고 이 도구가 승격하지 않습니다. 한 요청은 최대 100명이고 동일 학생 또는 계정의 중복 항목을 거부합니다. 다른 기수 추가는 별도 요청 ID로 승인합니다.

    명시적 적용과 재시도¶

    정책·계정 지정·백업 확인을 마친 격리 DB에서 먼저 실행합니다. --expect는 계획의 연결 항목 수이며 --confirm-target은 앞서 출력된 DB 확인값입니다.

    npm run academic:backfill -- --apply --plan=/안전한/경로/승인계획.json --expect=1 --confirm-target=출력된확인값

    대상 DB 확인값, 건수, 지정 책임자, 저장 활성화 조건 중 하나라도 다르면 적용하지 않습니다. 처리 중 대상 계정의 역할·회원 기수가 달라졌거나 삭제됐으면 전체 요청을 거부합니다. 기존 다른 계정으로의 교체와 연결 해제는 지원하지 않습니다. 한 계정을 다른 학생에 중복 연결할 수도 없습니다.

    학생·대상 계정 잠금, 연결, 기수 등록, academic_enrollment_link_batches 감사 기록은 원자적으로 확정합니다. 감사에는 승인자·승인 근거 참조·시각·이전/이후 ID·등록 생성 여부만 남습니다. 동일 requestId와 동일 계획 재시도는 기존 결과를 돌려주며 추가 행을 만들지 않습니다. 같은 requestId의 다른 계획은 거부합니다. 새로운 requestId로 이미 완료된 연결·등록을 승인하면 변경 건수 0으로 기록합니다.

    실행 중 종료되었으면 새 요청 ID를 만들지 말고 같은 계획을 재실행합니다. 커밋 전 종료는 전부 취소되고, 커밋 후 응답 유실은 저장된 감사 결과로 판별됩니다. 오류 원문에는 개인정보가 섞일 수 있어 도구가 고정 오류 메시지만 출력합니다. 운영 복구는 감사의 이전 ID와 백업을 검토한 별도 승인 절차로 처리하며 일괄 연결 해제·감사 삭제를 하지 않습니다. 탈퇴·연결 해제·보존 기간·파기는 #142 이후 별도 구현합니다.
