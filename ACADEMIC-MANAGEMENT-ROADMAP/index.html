    HRA 학사관리 전환 계획 — 현재 G1과 후속 단계¶

    상태: G1 코드 구현·격리 검증 / 운영 미활성, G2/G3 설계 · 기준: 2026-10-16, #144~#158 구현·격리 검증. 이 문서는 기존 HRA 사이트를 가벼운 학사관리(SIS + LMS)로 확장하기 위한 방향과 구현 순서를 정의한다. #144~#156의 학생 명부·과제·개인 제출·비공개 파일·화면 코드가 구현됐지만 운영 출시는 아니다. 관측·통합 CI(#157·#158) 코드와 격리 검증도 포함하며, 보존·파기·백업 정책(#142)과 G2/G3 운영 규칙(#143)은 미정이다. 기능·쓰기·업로드·정리 설정의 기본값은 비활성이다. 위 운영 상태는 기존 검증 시점의 기록이며, 2026-10-18 문서 검토에서 실제 운영 값을 다시 조회하지 않았다. 코드 병합·격리 검증과 운영 DB 적용·실제 학생 자료 저장·기능 공개를 구별한다.

    처음 읽는 분을 위한 순서¶

    이 문서는 무엇을 어느 단계에 구현하는지를 정한다. G1은 학생 명부와 개인 과제 제출, G2는 출결, G3는 피드백·수료 단계다. 기능 설정이 켜져야 다음 기능을 사용할 수 있다는 뜻의 “게이트”와, 운영 정책 승인도 구분한다.

    먼저 2절의 현재 기능과 3절의 단계 표를 읽는다. 학생이 어떤 일을 하는지 알고 싶으면 과제 제출 범위, 저장 구조를 바꾸려면 데이터 모델, 운영 데이터를 다루려면 보존·파기 정책 초안을 이어서 읽는다. “학적·대상 스냅샷·멱등성”은 용어집에 설명했다.

    1. 목표 및 성공 기준¶

    • HRA의 기수별 1년 교육을 학생 개인 중심으로 기록한다. 모집 → 등록 → 수업 → 과제 → 출결 → 수료 흐름을 단계적으로 연결한다.
    • 기존 Next.js 16 / NextAuth / Neon PostgreSQL / Drizzle / Vercel Blob 구조를 우선 재사용한다. 별도 ERP, 마이크로서비스, 학점·수강신청 시스템을 도입하지 않는다.
    • 첫 번째 운영 가능한 산출물(MVP)은 기수별 대상 학생 전원이 표시되는 과제 제출 현황이다. 미제출자는 제출 데이터가 없어도 명단에 나타나야 한다.
    • 공개 사이트·홍보 콘텐츠 관리·현재 자료실의 동작은 유지한다. weekly_texts와 class_logs는 공동 학습 콘텐츠이며 학생별 제출물로 재해석하지 않는다.
    • 승인된 사용자라도 자기 학적에 해당하는 과제와 자기 제출물만 조회한다. 파일 주소만으로 비공개 제출물에 접근할 수 없어야 한다.
    • 오류·취소·동시 제출·네트워크 재시도 상황에서도 동일 과제의 제출 상태가 일관되며, 과거 기록이 예기치 않게 삭제되지 않아야 한다.

    실제 수업 운영 주체 (2026-10-13 확인)¶

    • 교수(FACULTY)는 출결 업무를 담당하지 않는다. 교수의 수업·학습 내용 담당과 과제 피드백 권한은 별도로 검토한다.
    • 각 수업의 출결은 해당 기수에 배정된 운영 인력이 담당한다. 최종 정정·승인 절차는 #143에서 확정한다.
    • 수업 운영 인력은 어드바이저 1명과 조교 2명이다. 세 사람이 돌아가며 출결을 체크한다. 따라서 출결 입력 권한은 어드바이저뿐 아니라 조교에게도 필요하다.
    • 어드바이저와 조교는 기수마다 다른 사람이며, 한 기수 안에서는 수업마다 바뀌지 않는 고정 배정이다. 다만 조교는 학기 중에 바뀔 수 있고 향후 역할도 바뀔 수 있으므로, 배정은 기수·역할(어드바이저/조교)·기간(시작·종료)을 함께 기록해 변경 이력을 남기고, 교체된 사람의 권한은 종료 시점에 회수한다.
    • 이들을 관리하는 담당자가 따로 있으며, 홈페이지 관리자(ADMIN)와 다른 사람이다. ADMIN 은 홈페이지만 관리한다. 따라서 ADMIN 이라는 이유만으로 출결·학사 운영 권한을 주지 않고, 운영 인력 배정·교체와 출결 감독은 별도의 학사 운영 관리 권한으로 분리한다. 이 권한의 구체적 범위(출결 최종 승인, 학적·과제 관리 포함 여부)는 #143에서 확정한다.
    • 어드바이저·조교는 최초에는 특정 기수에 기간을 정해 배정되는 업무상 역할로 취급한다. 현재 전역 users.role에 해당 역할이 없으며, 승인 없이 역할 enum을 확장하거나 교수의 facultyId를 운영자로 재사용하지 않는다.
    • 학사 운영 관리 담당자의 감독·예외 처리와 운영 인력 부재·교체·대리 입력 규칙은 #143에서 확정한다. 관련 구현: #165.

    기수 cohorts와 기수별 ENROLLED 학적·다중 기수 이력(#144~#146) 휴학·탈퇴·수료 상태 전환은 미구현
    수업 schedule_events + schedule_sessions 및 과제의 선택적 수업 연결(#147) 출결·기수별 운영 인력 배정은 미구현

    품질 기존 CI, 학적·제출·파일 인가의 격리 PostgreSQL 및 실제 HTTP·브라우저 검증 코드 관측·G1 전용 통합 CI 구현. 운영 백업·보존·복구 승인은 후속 확인

    기존 사용자 역할 ADMIN / FACULTY / MEMBER / PENDING은 인증/시스템 접근권한으로 유지한다. G1 학적에는 별도 도메인 상태 ENROLLED만 구현됐으며, COMPLETED / WITHDRAWN 등의 추가 상태와 전환은 후속 정책 확정 전까지 제안이다.

    3. 단계별 범위 (출시 게이트 순서)¶

    단계 범위 완료/출시 게이트 제외
    G0 기존 기반 안정화 권한·자료/Blob 보안, 삭제·원자성, 테스트 DB와 CI 기반 #89, #88, #91, #97, #101, #103, #109 등 관련 이슈의 위험 검토와 필수 보완 완료 신규 학사 UI
    G1 학생명부·과제 MVP 운영 규칙, 학적 연결, 과제 등록, 개인 제출/상태, 인증된 파일, 학생·관리자 UI 기수별 대상/미제출/제출 전수 확인, 우회 접근 차단, 업로드 실패·재시도 검증 출결·학점·평가·피드백·수료 판정
    G2 출결·운영 인력 기수별 어드바이저·조교 기간 배정, 출결 입력·정정 이력, 학생 본인 조회 유효하게 배정된 운영 인력만 출결 입력, FACULTY/ADMIN 역할만으로 출결 불가, 미입력·결석 분리와 역할·기수별 접근 테스트 점수·자동 수료·교수 출결 업무
    G3 평가·수료 운영진 승인 후 과제 피드백·수료 요건·수료 확정 과거 이력 보존, 변경 감사, 예외 승인·취소 테스트 GPA·복잡한 학과·학점제
    G4 선택적 운영 고도화 알림·통계·상담 등 검증된 반복 업무 명확한 수요·개인정보 영향 분석·운영 책임자 확보 필요 미확인 기능

    G1에서 시스템이 수료를 자동 판단하지 않는다. 출결·평가 정책은 G2/G3의 별도 결정으로 둔다. 일정과 보고서 양식은 기존 기능을 재사용하며 중복된 학습과정/강좌 모델을 서둘러 추가하지 않는다.

    4. 사용자 여정 및 기능 단위¶

    운영진¶

    1. 기존 모집/지원서에서 합격을 관리한다. 합격만으로 계정을 자동 승격하거나 이메일이 같다는 이유로 기존 계정에 학적을 자동 부여하지 않는다.
    2. 신원과 참여 의사가 확인된 대상자를 특정 기수의 학적/학생명부에 등록한다. 같은 기수·동일 학생의 중복 등록을 차단한다.
    3. 해당 기수의 과제를 생성·수정·공개하고 선택적으로 기존 수업일/세션에 연결한다.
    4. 최초 공개 대상(assignment_targets) LEFT JOIN 최종 제출 방식으로 제출·미제출을 구분한다. 공개 뒤 명부가 바뀌어도 당시 대상과 분모를 유지한다. G1은 마감 후 제출을 차단하므로 지각 상태를 만들지 않는다.
    5. 학생별 파일 열람은 객체 수준 권한을 재검증한다. 과제 변경과 파일 전달 허가의 감사 기록은 구현돼 있다. 공개 후 과제·최종 제출의 일반 삭제는 제공하지 않으며, 삭제 절차와 내보내기 감사 확대는 별도 정책·구현으로 다룬다.

    학생¶

    1. 로그인 후 본인의 활성 학적을 조회한다. 소속 기수가 없거나 승인 대기라면 분명한 안내를 표시한다.
    2. /member/assignments에서 자신에게 공개된 과제와 마감·제출 여부를 확인한다.
    3. 허용된 형식의 파일을 안전하게 업로드하고 최종 제출을 확정한다. 업로드는 제출 완료와 동의어가 아니다.
    4. 본인의 제출물과 시각만 확인한다. 타인의 제출물 URL/ID 추측·직접 호출이 실패해야 한다.

    수업 운영 인력(어드바이저·조교) — G2 담당¶

    • 기수별·역할별 기간 배정으로 어드바이저 1명과 조교 2명의 출결 입력을 관리한다. 정정·최종 승인 범위는 #143에서 결정한다.
    • 로그인 계정과 해당 수업일의 기수에 유효한 운영 인력 배정을 함께 검증해야 출결 입력에 접근할 수 있다. 단지 MEMBER·FACULTY·ADMIN이라는 이유로 출결 권한을 주지 않는다.
    • 다른 기수의 출결과 학적 정보는 열람하지 않는다. 본인 배정 종료 이후 즉시 권한을 상실해야 한다.

    교수진 — 수업 내용 및 승인된 과제 검토¶

    • 본인 계정에 연결되고 담당자로 지정된 수업/과제만 검토한다.
    • FACULTY 역할만으로 모든 기수의 개인 제출물을 열람시키지 않는다.
    • 기존 홍보용 faculty 프로필과 로그인 users는 현재 별도이며, 검증된 연결이 필요하다.
    • 교수는 출결 담당자가 아니다. 교수 역할·수업의 facultyId로 출결 열람·입력·정정 권한을 부여해서는 안 된다. 교수의 과제 검토는 별도 정책에 따른다.

    G1 운영 승인자: 이번 정책을 승인한 HRA 운영 책임자 본인이다. 검증된 로그인 계정 ID로 지정하는 인가를 사용하며 ADMIN 역할만으로 학사 승인 권한을 부여하지 않는다. G2 출결 운영 인력의 배정·감독·정정 권한은 별도 #143에서 확정한다. G1 인가는 명부·과제 관리·전체 제출 현황·허용된 파일 조회에 적용되며, 운영 활성화는 별도다.

    서버 액션·메타데이터·파일 다운로드 API·관리자 조회에 동일 정책을 적용한다. 화면 숨김이나 Next Proxy 단독으로 인가를 대신하지 않는다. 개별 기수 간 공동 자료 열람 범위는 기존 #100에서 정책 결정하며, 개인 과제 파일 보호와 혼동하지 않는다.

    6. 데이터·보존·마이그레이션 원칙¶

    • G1 학적의 정본은 구현된 academic_students와 cohort_enrollments다. 기존 users.cohortId는 전환 기간에만 호환 필드로 유지하고 당장 삭제하거나 자동 덮어쓰지 않는다.
    • 과제와 제출 파일은 명시적인 소유권/참조 관계로 기록한다. 제출 파일에 access: public을 사용하지 않는다.
    • 운영 기록의 변경은 누가/언제/무엇을/왜 바꾸었는지 감사할 수 있어야 한다. 감사 로그에는 민감한 자유서술 본문·파일 URL 전체를 적지 않는다.
    • 기수·학생 계정의 일반 삭제로 제출/출결 기록이 묵시적으로 연쇄 삭제되지 않도록 FK 정책을 확인한다. 합법적인 개인정보 삭제 요청은 별도 명시적 절차로 구현한다.
    • 백필은 읽기 전용 점검 → dry-run → 격리 DB 마이그레이션 검증 → 운영 승인 → 적용/검증 단계로 처리한다. 계정 이메일 일치만으로 지원서나 과거 학적을 자동 연결하지 않는다.
    • Asia/Seoul 달력 날짜와 정확한 시각(UTC instant)을 혼동하지 않는다. 공개 과제의 마감은 KST 입력을 UTC instant로 저장하고 서버가 정각부터 제출을 차단한다.
    • 기존 Drizzle 스키마와 DB 마이그레이션 이력이 일치하는지 검증하며, 운영 DB에 drizzle-kit push만을 무검토 실행하지 않는다.

    상세 스키마·인덱스·경합 조건은 학사 데이터 모델, G1 과제 범위는 과제 제출 1차 범위에 정의한다.

    7. 운영 정책 결정 현황¶

    결정 ID 확인할 항목 결정 또는 남은 사항 결정 결과가 미치는 범위
    D1 대상 학생 정의 확정: 운영 책임자가 검증·수동 승인한 cohort_enrollments 전체 명부 및 미제출 집계
    D2 합격→등록·계정 연결 확정: 명단·본인 확인 후 같은 책임자 승인, 이메일 자동 매칭 금지 개인정보·계정 인계
    D3 과제 파일 개수/형식/상한 확정: 비어 있지 않은 PDF 1개, 최대 50MiB, 확장자·MIME·시그니처 검증 UI·DB·업로드 설계
    D4 마감 후 제출 확정: 공개 시 미래 마감 필수, KST 정각부터 최종 제출 차단 서버 시각 검증
    D5 교체/재제출 확정: 최종 제출 후 교체·재제출 불가, 동일 요청 멱등 재조회 허용 이력·경합·고유 제약
    D6 교수진 제출물 검토 G1은 지정된 운영 책임자만, G2에서 담당 교수 정책 결정 교수 매핑·권한
    D7 학적 상태/탈퇴·수료 G1에선 학적 식별/등록만, 종료·수료는 G3 보존·학생명부 집계
    D8 보존·파기/열람 목적 부분 결정: 최종 관리 승인자는 이번 결정을 내린 HRA 운영 책임자 본인. 저장 종류별 기간·파기 트리거·요청 대응은 #142에서 미정. 승인용 초안 참조 개인정보·백업·감사
    D9 수업 운영 인력의 출결 운영 절차 확인: 교수 출결 미담당 / 어드바이저 1명·조교 2명이 돌아가며 출결 체크 / 기수마다 다른 인력, 기수 내 고정 배정이나 조교는 학기 중 변동 가능·향후 역할 변경 가능 / 이들을 관리하는 담당자는 홈페이지 ADMIN 과 다른 사람. 정정·최종 승인 절차와 학사 운영 관리 권한의 범위는 #143에서 확정 #165 운영 인력 배정·권한·#159 출결·#160 화면

    확정된 G1 규칙의 상세·수용 테스트는 학사 데이터 모델과 과제 제출 범위에 기록한다. 남은 결정은 GitHub question 이슈로 확인하고 미정 조건을 승인된 요구사항으로 구현하지 않는다.

    8. 완료 정의와 추적¶

    • 신규 서버 기능은 검증된 입력 스키마, 역할+기수+대상 객체 권한 검증, 유일/외래키 제약, 실패 후 재시도와 감사 경로를 갖춰야 한다.
    • DB/Blob 쓰기는 성공/실패/응답 유실/동시 실행에서 불변조건을 테스트한다.
    • 격리된 테스트 DB·테스트 Blob만 사용하고 실제 학생 자료와 실제 URL을 테스트/이슈에 올리지 않는다.
    • CI의 lint/typecheck/unit/build와 구현된 G1 통합·E2E 게이트를 유지한다. 현재 실행 범위는 G1 품질 게이트에서 확인한다.
    • 과제 제출 E2E는 기수 A 학생, 기수 B 학생, 승인 대기, 교수진, 관리자, 업로드 실패, 중복 제출, 마감 경계, 비공개 파일 다운로드를 포함한다.
    • G2 출결 E2E에는 해당 기수에 배정된 어드바이저·조교 / 배정이 종료된 인력 / 다른 기수 배정자 / FACULTY / 학생 / ADMIN / PENDING을 포함한다. FACULTY·ADMIN 역할만으로 출결 입력을 허용하지 않는다.
    • 운영진에게 보여 줄 상태 지표(기수별 전체 대상/제출/미제출/장애)를 명확히 정의한다.
